# First-version implementation

This file records the first version's mechanisms and verification boundaries.

## Components and pinned integration

Python 3.12 runs one local Prefect 3.8.8 server with SQLite, a native process Runner, definition watching via watchfiles, and the lifecycle controller. Swift/AppKit supplies the menu bar, workspace selection, ServiceManagement login toggle, UserNotifications delivery, and a Network-framework loopback webhook endpoint. JSON over inherited stdin/stdout connects the app to the controller; there is no extra network control API.

The menu bar uses the Searchlight silhouette: an 18-point vector template image in a fixed 30-point slot. AppKit supplies light/dark/highlight coloring. Ready shows a steady right-facing beam; active work alternates two beam angles every 0.8 seconds; paused scheduling replaces the beam with pause bars; disabled automation removes it; an error replaces it with an exclamation mark. Active work takes precedence over disabled/paused while draining; errors take precedence over activity. Images are cached, no animation timer runs while idle, and Reduce Motion suppresses animation. Tooltips and accessibility labels include the phase, pause state, and active count.

### Grouped menu and task artifact access (October 17 follow-up)

The top level keeps status/workspace name, Active Tasks, Recent Activity, the Prefect dashboard, Automation, Notifications, Workspace, Settings, and graceful Quit. The last-reported host/time is inside Workspace. Notification mute, scheduling pause, and login startup attention appear on their parent groups. Immediate stop remains available while disabled work is still draining. AppKit automatic item validation is disabled; unavailable actions have explicit enabled states. Controller heartbeats update state/icon without replacing the tree while a menu is being tracked.

Active Tasks means all configured managed tasks except deployments paused in Prefect or with every existing schedule inactive. Tasks without schedules remain eligible. Global scheduling pause leaves artifact/manual-run shortcuts available; global automation disable stops Prefect and shows an unavailable explanation. Each task submenu contains its latest observed run state, full artifact, latest non-scheduled run, deployment page, and Run Now. Empty/configuration/lookup-failure/no-artifact states are distinct. Snoozing notifications does not remove a task from Active Tasks.

`watcher/task_menu.py` reads the pinned Prefect 3.8.8 REST API using deployment filters, `START_TIME_DESC` for non-scheduled runs, and `CREATED_DESC` for artifacts excluding `result`/`progress`. This avoids scanning a bounded number of recent runs and losing a report when later runs have no output. A report from a failed/in-progress run is still eligible if the task explicitly published it; Watcher does not infer semantic completeness of Markdown content. Unkeyed artifacts work. `save_output` blobs/serialized return values are separate storage and are not exposed as Prefect artifacts.

The controller sends `task_menu`, `task_menu_error`, and `can_run` with status. A `task_menu` pipe command refreshes on opening the root menu, with an initial lookup at engine start; there is no extra timer or server. The task submenu reads the newest received state when opened. A refresh arriving after it opens is visible on reopening. The `latest_artifact` command resolves again at click time and emits a workspace-scoped `open_artifact` UUID; the companion opens `/artifacts/artifact/{id}`. Run/deployment links use the installed V2 UI's routes. These routes and filter schemas were confirmed against the installed official Prefect source/UI bundle. Lookup errors clear cached links without stopping scheduling. Menu state is ephemeral and cleared on stop/switch; it adds no private files or snapshot schema.

Validation: the full suite passed **36 tests in 206.57 seconds**. Build and strict signature verification passed. New checks inspect the production AppKit tree, grouped/empty/unavailable states and action routing, API failure isolation, deployment/schedule filtering, unkeyed reports, exclusion of newer progress/unrelated artifacts, and resolving a report published after the menu lookup despite a newer run without output. Synthetic integration data establish report access. Actual hover traversal and browser navigation through a clicked native item remain manual validation.

The version-sensitive Runner adapter is in `watcher/runner.py`, with hook execution in `watcher/hooks.py`. Prefect 3.8.8 moved execution into `ScheduledRunPoller`, `EngineCommandStarter`, and `ProcessManager`; simply overriding the older `_run_process` facade would not select the task environment. The adapter registers managed deployments, selects immutable validated entrypoints and the separate task Python, filters automatic admission for pause/freshness, and uses native process-group cancellation. Cancellation/crash hooks execute in the task environment against the validated code image; the native default hook loader would otherwise download workspace contents into the controller working directory. Ordinary process stdout/stderr are forwarded to native retained Prefect run logs. Capacity and deployment concurrency remain Prefect's defaults. The adapter uses private version-sensitive interfaces and must be retested before an engine upgrade.

Source inspection and integration testing confirmed:

- Native `serve` defaults to pausing deployments on shutdown. Watcher sets `pause_on_shutdown=False` to preserve deliberate dashboard pause and overdue work.
- Native Runner stop cancels work. Watcher closes admission and waits for process-manager/submission counts to reach zero before calling it, except for explicit immediate stop.
- Deployment upserts reset schedules; deployment updates also delete future auto-scheduled runs. Unchanged definitions and code-only edits therefore avoid API updates. Changed schedules retain operational active/paused state.
- Prefect's scheduler is bounded. Replay uses server schedule date generation and the real `/deployments/{id}/schedule` endpoint, preserving native idempotency keys. A client schedule object alone has no `get_dates` method in this version.
- Prefect's default block-encryption key is stored in its `configuration` table and is covered by the database backup. Watcher does not inherit external Prefect configuration or an external encryption-key override for its server.
- SQLAlchemy 2.1.5 caused `InvalidRequestError` in native scheduled-run insertion. The application constrains SQLAlchemy to 2.0; the tested lock resolves 2.0.55.

Official references: [local serving](https://docs.prefect.io/v3/how-to-guides/deployment_infra/run-flows-in-local-processes), [scheduling](https://docs.prefect.io/v3/concepts/schedules), [Prefect source at v3.8.8](https://github.com/PrefectHQ/prefect/tree/3.8.8/src/prefect), [SQLite online backup](https://www.sqlite.org/backup.html), [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), and [Frankfurter](https://frankfurter.dev/).

## First-launch workspace setup

The root `./install.sh` is the entry point for first installation and explicit updates from the current checkout. It delegates to the existing system-Python setup, which holds the engine's instance lock while provisioning the locked application environment, building/signing `build/Watcher.app`, and recording installation paths. A held lock produces instructions to quit gracefully and retry before any environment or app replacement. Installation preserves local runtime, workspaces, and preferences. Run `./start.sh` afterward to launch the new binary; changing native source alone does not update a running app. `scripts/setup.sh` remains available and `scripts/update.sh` delegates to the root installer.

Login startup uses `SMAppService.mainApp`. When the saved preference requests startup, both `.notRegistered` and `.notFound` trigger registration. Handling `.notFound` fixes missing login records after reboot. The menu reads the actual OS status whenever it opens, shows a tick only for `.enabled`, and shows a mixed mark plus a settings action for `.requiresApproval`. Registration errors live separately from engine state so controller messages cannot erase them. Failed registrations can be retried from the menu. The read-only `--login-status` native argument reports the actual registration and saved preference without starting the engine or requesting registration.

Login regression validation: strict signature verification and **5 checks** (the injected native login lifecycle regression plus all four existing native smoke cases) passed in 8.96 seconds. A physical login remains the end-to-end check. The regression uses injected registration closures and never modifies real login items.

The companion offers Create Workspace, Open Existing Workspace, and Try the Example when no workspace is remembered. The same actions remain in the menu. Creation and validation run asynchronously through the installed Python CLI, sharing its external-root and workspace-format checks. A failed selection leaves the current controller running; successful selection uses the existing graceful switch. The selected path is remembered when the controller reports its workspace, rather than before validation. Cancelling the welcome/folder dialog leaves the app idle and its menu available.

Try the Example initializes `~/Library/Application Support/Watcher/Example Workspace` (under `WATCHER_LOCAL_HOME` in isolated tests). It is a persistent ordinary workspace, not an ephemeral mode. Repeating `init --example` validates and reuses an existing workspace without overwriting task code or configuration. Show Workspace in Finder exposes its files. Setup still builds a checkout-dependent app; CLI initialization is optional.

## Storage, snapshots, and recovery

Live runtime is local to this application checkout, in Git-ignored `.watcher-runtime/<workspace-id>/`. Its `prefect.db` holds native orchestration history/logs/artifacts/blocks and the default encryption key. Its `data.db` holds persisted result blobs, retained output blobs, baselines, deployment fingerprints, pause state, and catch-up cursors. The compact storage block resolves paths from the active workspace’s stable ID; no absolute storage root is embedded in the result block. `WATCHER_RUNTIME` exposes the runtime path to task processes, and the controller’s status message supplies it to the native notification bridge. `WATCHER_RUNTIME_HOME` overrides the runtime base for isolated tests and is propagated to subprocesses. Code, configuration, and authentication files are ordinary private synced files. Result/output data travel **inside snapshot bundles**, avoiding a second independently synchronized live database or thousands of per-run result files.

The controller and offline snapshot/restore/export commands migrate an older workspace’s `runtime/` while holding the instance lock, before storage use. An atomic directory rename preserves databases, journals, logs, and code copies together; it removes the obsolete `DO-NOT-SYNC.txt` note. Validation/initialization helpers do not migrate a running workspace. Two populated runtime locations produce an explicit error instead of a merge. Cross-filesystem migration fails without copying/deleting source data; it requires an offline manual move. A workspace moved within the same Mac reuses its ID’s existing local runtime; another Mac reconstructs it from synced snapshots. No Insync exclusion is needed for the external workspace.

Snapshots take a SQLite online backup of both databases. Compact-store writers are briefly blocked while Prefect is captured first, then the compact store. This includes result bytes already referenced by the orchestration view; a concurrent run may still appear in progress, which is expected. Snapshots do not make external side effects transactional. Each bundle contains a manifest, workspace id, exact engine version, timestamps, SHA-256 hashes, and both databases. SQLite integrity is checked on creation and restoration. A `.partial` file is fsynced and renamed only after validation. Readers ignore partial/broken candidates. Rotation retains three valid published bundles.

Snapshots run hourly and after stopping the engine cleanly. Snapshot checksums prove completeness of a received artifact, not that Insync has finished synchronizing all other files. Healthy local runtime wins by default; explicit offline restore replaces it and preserves prior database/WAL files for diagnosis. A restore-in-progress marker retries an interrupted two-database replacement at the next start. A corrupt local database raises a visible recovery error instead of silently choosing an older snapshot. Different engine versions are rejected before replacement.

`watcher restore` and `watcher snapshot` take the same local OS lock as the controller. It is an advisory `flock` held on a non-inherited descriptor, not a synced lock file. A small pipe-lifetime guardian kills registered server/flow process groups if the controller is killed. Normal flow completion also closes its ordinary descendant lifetime. Deliberately detached processes and machine power loss remain outside process-group cleanup; power loss is handled by SQLite recovery/snapshots. Synced last-seen state never blocks startup.

History retention defaults to 90 days and uses Prefect APIs to delete terminal runs and their artifacts. A narrowly scoped SQLite delete handles old logs because Prefect exposes no bulk log-delete API. Unreferenced result blobs expire with the history window; blobs still referenced by retained results are preserved, and result garbage collection waits for an idle admission boundary; saved outputs have independent per-output expiry. Baselines/configuration/authentication do not expire. Cleanup runs at the hourly maintenance point. Retained snapshots can resurrect records already removed from the working database until the snapshots rotate; this is the separate three-snapshot rule. SQLite reuses freed pages; cleanup does not promise immediate file shrinkage.

## Definitions and dependencies

Only `tasks/` and `config/` are watched. Bursts settle before the full manifest is parsed and flows are imported in a separate task-environment process. An immutable content-addressed task-code copy becomes current only after successful validation. Active processes keep their previous code; invalid changes leave the last validated version runnable. Stable manifest ids distinguish renames from removals. Unused code copies are removed on an idle reconciliation; runtime/cache churn never triggers the watcher.

Task requirements are constrained by `requirements-engine.txt`, generated from `uv.lock`. Environments live outside synchronization and are separate from the app's `.venv`. Dependency changes close admission, drain, build a new environment keyed by dependency content, and only then resume. Old dependency environments remain as disposable local installations; there is no automatic arbitrary package upgrade. Errors stay visible and do not resume a partially prepared environment.

The workspace configuration controls `history_days` and `output_days`; both default to 90 and must be positive. Task-specific output expiry is passed to `save_output`. Synced task authentication uses explicit tool-specific paths under `auth/`. Watcher does not manage browser sessions.

## Notifications

A real ad-hoc signed app identity (`local.watcher.app`) hosts an authenticated HTTP endpoint bound to `127.0.0.1` on an ephemeral port. Its current address/token are written with mode 0600 to the local runtime. Requests include workspace identity, stable notification key, and optional run id. Wrong tokens and stale-workspace requests are rejected. Unexpected engine failure also triggers a companion OS-alert request when unmuted. The companion acknowledges after UserNotifications accepts the request; mute acknowledges without queuing. Last 2,000 accepted ids are retained in per-Mac preferences for retry/restart suppression. Workspace switches remove pending local notifications; clicks from old contexts do not open a run in the new database.

Notification acceptance does not prove visual presentation. Denied authorization/Focus and other OS settings can suppress it. Delivery failures use ordinary flow retry; no durable cross-channel router/outbox was added. Deduplication is local to a Mac and bounded, so migration to another Mac may deliver an observation again. Exactly-once notification delivery is not promised.

The Python helper uses Prefect's `{{subject}}` and `{{body}}` webhook placeholders. Regression checks exercise the real helper/block renderer, asserting the outgoing title/body (including Unicode and multiline text), authentication, routing, and delivery identity. The muted native bridge check also asserts the rendered title/body stored for snooze comparisons; it does not establish visible desktop presentation.

### Selective desktop snoozes (October 17 follow-up)

`native/NotificationSnoozes.swift` holds the policy and transaction store; `NotificationControls.swift` supplies the native chooser/management dialogs. The `watcher-alert` UserNotifications category registers a foreground **Snooze…** action. The menu also exposes **Snooze Notifications…** for previously observed alerts and **Silenced Notifications…** for inspection, early resume, and extension. Intervals are 1 hour, 3 hours, 12 hours, 1 day, 3 days, and 1 week. Scopes are one stable alert within a task, or all alerts of one task. The optional message-change checkbox defaults off. Hard snoozes survive new or changed messages. Breakable snoozes compare the displayed title/body hash against each alert's fixed baseline; a new alert also breaks a breakable task snooze. A break removes that rule entirely, including if the old message returns later. Independent overlapping rules continue to apply. Extension adds the selected duration to the existing expiry and keeps its baseline.

Preferences occupy one `notification_preferences` row in the existing `data.db`, including latest known alerts and active snoozes. Native SQLite uses transactions with a 60-second busy timeout, on a serial background queue, sharing the writer boundary already used by snapshot capture. Connections reopen for each operation, and no preferences are cached across runtime restoration. Expiry is a wall-clock timestamp. Snoozes are included in the normal hourly/shutdown snapshot with the same recovery-loss window. Disabled startup also restores snapshots, and disabled quit/workspace switch takes a snapshot if databases exist. The companion drains queued preference writes before sending quit/switch commands. Snapshot validation/backup connections now close explicitly before restore renames; the recovery regression exposed stale Python reads when a validation handle survived the move.

The Python helper accepts `alert_id` (default `default`) and optional `task_id`. The Runner sets `WATCHER_TASK_ID` to the stable manifest task id for each child. Multiple conditions in one task need distinct stable alert ids. A delivery `key` remains separate; absent an explicit key, it includes the inferred flow-run id, title, and body so repeated checks can notify again while identical retries deduplicate. Native delivery identities encode workspace/task/alert/key components without delimiter ambiguity. Legacy direct webhook payloads without new fields remain supported as alert-only notifications grouped by title. Identity scoping changed, so an occurrence accepted by an older app can be delivered once again after this update. The bounded 2,000-id per-Mac cache remains; it now records muted/snoozed acknowledgements too. In-flight duplicate requests return a retryable error until the first request completes. Settings failures return 503 instead of bypassing snooze. Tasks continue executing and other notification channels keep their existing behavior.

Automated checks exercise the production Swift policy/store, the real Prefect webhook block and authenticated native bridge with delivery muted, rollback, overlapping rules, title/body changes, new alerts, task isolation, restart persistence, expiry after downtime, snapshot recovery to fresh local runtimes, disabled recovery/shutdown, and corrupt-settings failure/retry. The native build registers/compiles the action and dialogs; actual Notification Center presentation and clicking the chooser remain manual verification items.

Follow-up validation: the full suite passed **28 tests in 182.91 seconds** outside the macOS sandbox, including all three new snooze checks and the existing lifecycle, backfill, storage, native, onboarding, login, and clean-setup regressions. The updated app built successfully and passed strict signature verification. No dependency versions changed.

### Recent notification history

**Recent Notifications** is a top-level native submenu beside Active Tasks. It shows the newest ten occurrences with relative ages and Muted/Snoozed labels, native full-text tooltips, and click-through to the history window. **View All Notifications…** opens the same native window: a selectable newest-first list, complete wrapping/scrollable message details, Copy Message, Open Run when the engine and linked run are available, and the existing Snooze chooser. Load Older fetches another 100 entries. System appearance, standard keyboard navigation, and accessibility labels are used. Opening history does not clear Notification Center or mark entries read. The menu tree remains stable while tracking; newer arrivals appear on reopening.

`NotificationHistory.swift` stores immutable occurrences in an indexed `notification_history` table in the existing private `data.db`, separate from snooze preferences. Each row contains the occurrence identity, wall-clock timestamp, original task/alert/title/body, optional run id, delivery status, and engine-alert marker. Unique ids preserve the first occurrence across duplicate writes/imports; separate delivery keys retain repeated messages from different runs. Sent entries are recorded after UserNotifications accepts the request. Muted and snoozed occurrences are also recorded, with Snoozed taking display precedence. Bridge success is acknowledged only after persistence; a history failure is retryable. This does not provide exactly-once OS presentation: acceptance and the history transaction are separate operations, so a crash or write failure between them can lead to another submission on retry.

The controller status now includes `history_days`, using the existing workspace setting (90 by default). History reads/writes prune expired records and use timestamp/id keyset pagination. Database connections open per operation on the serial notification queue, with the same SQLite writer boundary and timeout as snoozes/snapshots. History is included automatically in workspace snapshots, with their existing recovery-loss window. No additional synced files, databases, Python task APIs, or delivery replay queue are introduced. Quit/switch waits for in-flight delivery callbacks and queued history/preferences writes before requesting the controller's shutdown snapshot.

The companion caches only the recent workspace view, rejects stale asynchronous UI updates after switching contexts, and closes the old workspace's history window. History remains available with the engine disabled or unavailable. Engine-stopped messages receive unique occurrence identities and use the same store, including when globally muted. Workspace activation also imports that workspace's still-retained Notification Center messages using their original delivery dates. Imports deduplicate against existing history. Already removed notifications and older muted/snoozed occurrences cannot be reconstructed from the legacy latest-alert snooze baselines. Sent to macOS means submission was accepted, not that authorization/Focus allowed visible presentation.

Validation used an isolated source copy and synthetic external workspaces: **40 tests passed in 224.57 seconds**, with the existing Git-ignore case excluded because that copy has no Git metadata; an equivalent runtime-ignore probe passed through the authorized read-only wrapper in the real checkout. The final typography/keyboard follow-up passed the **15 notification/menu checks** separately. The isolated app built and passed strict signature verification. Automated checks exercise persistence and upgrades, retry identity/status precedence, write-failure/retry, timestamp pagination/retention, snapshots, engine occurrences, stale workspace callbacks, stable menu tracking, complete Unicode/multiline text, unavailable run links, keyboard selection, and empty/error states. Light/dark offscreen text/layout renders were inspected. Physical hover-tooltip interaction, VoiceOver speech, live banner disappearance/import, and actual on-screen button presentation remain manual OS checks. The running installation was not rebuilt or restarted.

Verification on October 17: the complete 11-test suite passed, followed by passing dependency-drain and clean-terminal-setup integration tests (13 tests total). The native application compiled and passed strict ad-hoc signature verification. All test workspace data were synthetic and external to the checkout.

The automated suite covers clean terminal setup/example initialization, dependency changes waiting for active work, synthetic compact results and file count, baseline/change/retry behavior, snapshot rotation and corrupt/partial fallback, recovery at another path, lock release/non-inheritance, real scheduled/manual execution, paused manual execution, deployment reload/removal/history preservation, invalid-code isolation, graceful/forced stop with child cleanup, 120-day backfill/idempotency, fresh-run collapse, encrypted-block recovery, retention, controller crash recovery, workspace switching, and the native authenticated webhook via Prefect's actual notification block.

The native smoke deliberately mutes notifications and disables login registration using isolated test preferences. It checks actual app startup, loopback authorization/workspace isolation, and controller cleanup when the app exits. Compilation and ad-hoc signing are also checked. A synthetic concurrent writer test verifies that every result referenced in a snapshot has corresponding bytes, and an interrupted restore marker is tested through automatic recovery.

Not end-to-end verified here: actual visual Notification Center delivery, launch at the next macOS login, Insync transfer, a second physical Mac, and real laptop sleep/wake. Time gaps and changed workspace paths are exercised synthetically. The app is not notarized and has no self-contained installer. Runtime logs and old dependency/recovery directories are diagnostic/local data; they are not synchronized.

Prefect's native crash policy does not guarantee automatic retries or exactly-once external effects after abrupt loss. A run interrupted while the API is unavailable may retain an uncertain Running state requiring inspection in Prefect. Watcher reports local process activity separately from historical API state. Immediate stop with a functioning server records cancellation. The implementation deliberately adds no global overlap queue, distributed lock, agent framework, or alternate dashboard.
